# Wispr Flow comparison for VoxKey

Public evidence checked on 2026-10-03. Wispr Flow's full private architecture, model weights, prompts, and production configuration are not published. These sources support a functional comparison, not a reconstruction of its internals.

## What is public

- Wispr describes context-aware and personalized speech recognition, a separate personalized LLM formatting stage, and a target of under 700 ms after speech ends. Its engineering note calls out speaker history, surrounding context, corrections, and application context as hard problems, not a complete implementation description. [Wispr engineering note](https://wisprflow.ai/post/technical-challenges)
- Wispr describes Canto as a proprietary real-time speech model trained with supervised fine-tuning and reinforcement learning. It reports evaluations on opted-in real dictation, difficult audio, and public datasets. Specialized dictionary vocabulary is supplied at runtime, with a documented risk of over-trusting similar terms. [Canto research](https://wisprflow.ai/canto)
- Baseten says Flow uses fine-tuned Llama models for transcript cleanup on dedicated AWS deployments and reports an end-to-end p99 target under 700 ms. That is a hosted implementation and is not an offline design for VoxKey to copy. [Baseten case study](https://www.baseten.co/resources/customers/wispr-flow/)
- Flow documents spoken punctuation, line and paragraph commands, list formatting, app-aware style, and correction handling. Its help page says Smart Formatting does not correct misheard words. [Smart Formatting help](https://docs.wisprflow.ai/articles/5373093536-how-do-i-use-smart-formatting-and-backtrack)
- Flow's dictionary accepts preferred words and phrases and explicit corrections. [Dictionary help](https://docs.wisprflow.ai/articles/4052411709-teach-flow-your-words-with-the-dictionary)

## VoxKey today

`voxkey_app.py` records 16 kHz mono audio and queues a job. `SpeechModelManager` in `speech_models.py` transcribes with local faster-whisper `small.en` by default, or a selected local `distil-large-v3`, using a one-candidate beam, VAD, and optional vocabulary prompt. `VoxKeyController` passes the transcript to `WritingModelClient`; that client uses local Ollama `qwen3.5:0.8b` or a fast deterministic path for long, already formatted, or explicitly commanded dictation. The controller then pastes into the captured foreground window. `VoxKeyRuntime` owns local settings and diagnostics. No stage sends dictation to Wispr or another cloud service.

The earlier log sample contained 53 transcription timings and 38 completed polish/paste timings: medians were 1,391 ms for transcription, 1,539 ms for polish, and 3,562 ms from processing start through paste. These are historical timings, not the current personal benchmark. The C: drive retains only the latest VoxKey WAV, replacing it after each dictation. A production-style GPU benchmark and three labeled personal clips are now available locally under ignored `benchmark/local_samples/`.

## Quality direction within the offline architecture

The writer requests formatting without grammar rewrites and checks that its output keeps the dictated words in order. A rewrite, poor casing, or truncation uses local punctuation and capitalization on the original transcript. Explicit line, paragraph, bullet, and punctuation commands take that fast path directly; so do long or already formatted transcripts. This protects recognized words and removes writer delay on those paths. It cannot recover a word that the speech model already misheard.

The three prompted personal clips establish an initial accent comparison. More spontaneous and noisy clips would narrow uncertainty. Wispr Flow output for the same clips is unavailable, so a direct Flow accuracy claim remains unverified.

The benchmark uses the same speech-model manager and decoder settings as production, with optional labeled Flow output in its manifest. On 12 public accented-English clips (344 reference words), `small.en` scored 17.2% word error rate with 1.31 seconds median warm GPU transcription, and `distil-large-v3` scored 12.2% with 2.18 seconds. Distil was better on nine clips, equal on one, and worse on two. Beam sizes 3 and 5 and `hotwords` did not fix tested term errors, so beam 1 remains. These clips are a public proxy.

On three prompted recordings from this user (32 reference words), `small.en` scored 6.25% word error rate versus 15.6% for `distil-large-v3`. Both counted “version three” → “version 3” as one WER error; both heard “cache” as “cash.” Distil additionally missed “VoxKey” and “Wispr Flow.” Beam sizes 3 and 5 made no change. Adding “cache” to the vocabulary changed both “cache” and “cash” to “cache,” so that bias was rejected. Warm speech times for `small.en` were 1.57, 0.85, and 0.85 seconds, versus 3.04, 1.97, and 1.98 seconds for distil. This small controlled sample supports selecting `small.en` on this PC, not a universal model ranking.

For short dictation, the 0.8B writer can return text without punctuation or in title case. The formatting guard now falls back to local sentence formatting in those cases and restores the user's chosen vocabulary casing. Nine of the 12 public speech outputs were already formatted; sending them through the writer consumed roughly 1–3 seconds each and once produced erratic capital letters. Their fast path now takes about 2 ms median, leaving the Ollama stage for unformatted short text. A local 2B Q4 writer trial changed words in two of four controlled sentences and briefly left only 31 MiB free GPU memory while the current writer was also resident. It was unloaded and removed; the 0.8B writer remains selected.

The 2.3.0 personal installer was installed in place and its executable matched the build by SHA-256. With `distil-large-v3`, startup took about 29 seconds, the process working set was about 401 MiB, and 1,584 MiB GPU memory remained free. After the personal comparison, the saved model selection changed to `small.en`; the installed app reached Ready in about 8.5 seconds, used about 399 MiB working set, and left 2,256 MiB GPU memory free. An initial 1.59-second hotkey recording on 2026-10-04 produced no transcript or paste; its RMS audio level was 62 versus 199–223 on the prompted clips. Two later installed-app dictations logged successful paste. The latest retained WAV independently transcribed as “Git should sync with GitHub before I ship version 3.”, matching the user's reported Notepad output. That dictation took 1,047 ms for speech recognition, 16 ms for formatting, and 1,594 ms from processing start through paste. After dictation, the app process had a 579 MiB working set and 2,180 MiB GPU memory remained free; these are point-in-time measurements, not a sustained peak.

Hardware: Ryzen 5 5600H, 16 GB RAM, GTX 1650 with 4 GB VRAM. The public clips above are from the [MIT-licensed EkaCare ASR evaluation dataset](https://huggingface.co/datasets/ekacare/eka-medical-asr-evaluation-dataset). A large-v3-turbo candidate previously needed 5.9 seconds warm on one 28.5-second local recording and was rejected. Model downloads contain no private audio.
